# 温泉オントロジー（Onsen Ontology）

日本の温泉に関する**法制度・分類体系**を OWL / RDF でモデル化し、SPARQL 推論と Amazon Bedrock の tool calling を組み合わせて「温泉爺エージェント」を動かすプロジェクト。

> **免責事項**
> 本リポジトリは知識表現の技術検証物であり、**医療的助言ではありません**。適応症・禁忌症・入浴プロトコルの記載はすべて環境省「温泉法第18条第1項の規定に基づく掲示基準」（環自総発第1407012号、平成26年7月1日）の条文内容の引用であって、個人の健康判断の根拠として用いるべきものではありません。温泉療養を行う場合は、同基準自体が「専門的知識を有する医師による指示、指導のもとに行うことが望ましい」と定めています。

## セットアップ

```bash
uv sync
uv run onsen stats     # 動作確認（初回は OWL 推論に25秒ほどかかる）
```

エージェント（`onsen ask`）を使う場合のみ AWS の認証が必要。設定は `.env`（git 管理外）に置ける。

```bash
cp .env.example .env   # AWS_PROFILE / AWS_REGION / ONSEN_BEDROCK_MODEL_ID を書く
aws sso login --profile dev-vm
```

`.env` はカレントディレクトリから上に辿って探し、**既にシェルで export されている環境変数は上書きしない**。export で直接渡してもよい。

```bash
export AWS_PROFILE=dev-vm
export AWS_REGION=ap-northeast-1
# 既定は Japan クロスリージョン推論プロファイル jp.anthropic.claude-sonnet-4-6（推論が日本国内で完結する）。
# アカウント固有のアプリケーション推論プロファイルを使うなら ARN を指定する
export ONSEN_BEDROCK_MODEL_ID='arn:aws:bedrock:ap-northeast-1:<account-id>:application-inference-profile/xxxx'
```

既定のモデルはアカウントでアクセスを有効化しておく必要がある。アカウント固有の ARN はコードに埋め込まず、`.env` か環境変数から読む。

## CLI

| コマンド | 説明 |
|---|---|
| `onsen stats` | グラフ統計と推論ルールごとの発火数 |
| `onsen facilities` | 全施設一覧 |
| `onsen facility <名前>` | 施設の詳細（源泉・pH・区分・湯使いと理由・飲用許可・出典） |
| `onsen quality <泉質名>` | 掲示用泉質の詳細（判定基準・適応症・禁忌症・仕上げ湯関係） |
| `onsen symptom <口語>` | 症状の口語表現から施設を検索 |
| `onsen protocol` | 法定の入浴・飲用プロトコルと一般的適応症・禁忌症 |
| `onsen drinking <源泉名>` | 含有成分別禁忌症（飲用）の限界飲用量を計算 |
| `onsen plan [--area X] [--facilities A B C]` | 巡浴プランの生成・検証 |
| `onsen ask <相談>` | 温泉爺エージェントに相談（Bedrock を呼ぶ） |
| `onsen consult [相談...]` | 湯治コンシェルジュとして複数ターン相談（対話モードあり） |
| `onsen eval` | オントロジーの効果検証（ablation）を実行・集計 |
| `onsen corpus <build\|align\|search\|stats>` | 比較実験用のコーパスを構築・検索（`build`=Web から取得 / `align`=グラフから揃えた生ドキュメントを生成） |
| `onsen graph <切り口>` | グラフの一部を図にする（DOT / PNG / SVG） |

`onsen plan` の主なオプション: `--adapted`（温泉に慣れている）、`--minutes`、`--gap`、`--days`（連続療養日数）、`--high-temp-caution`、`--max-baths`。

`onsen ask` の主なオプション: `--show-tools`（ツール呼び出しを表示）、`--revise`（検算の指摘を差し戻して書き直させる）、`--no-verify`（検算しない）。

`onsen consult` の主なオプション: `--no-repair`（未出典の語を自動で裏取りしない）、`--no-carry-over`（指摘を次ターンに申し送らない）。

`onsen eval` の主なオプション: `--dry-run`（呼び出し計画だけ表示）、`--conditions`／`--questions`（条件・問を絞る）、`--report`（保存済み JSONL を集計、複数指定で合算）。既定は A〜D の4条件で、`--conditions F G H` を付けると追試の3条件も走る。

実測結果は `eval-results/*.jsonl` にコミットしてある（504サンプル＋Phase 6 の192サンプル）。**回答文もすべて入っているので、記事の数字は誰でも再集計できる**（`uv run onsen eval --report eval-results/phase7*.jsonl`）。モデル ARN はアカウント ID を含むので `scripts/sanitize-eval-results.py` でモデル名に置換してある。

`onsen graph` の切り口は3つ。`schema`（クラスとプロパティ）、`facility`（1施設のサブグラフ。`--facility 名前`）、`quality`（掲示用泉質10種と適応症・禁忌症）。**推論で増えた辺は赤い点線で描く**ので、書いた事実と導いた事実が図で区別できる。PNG/SVG には graphviz が必要（`--format dot` なら不要）。

```bash
uv run onsen graph facility --facility 大滝乃湯 --out ohtakinoyu.png
uv run onsen graph quality --format svg --out quality.svg
```

```
├── onsen_instances.ttl    実データ（ABox）: 15温泉地・27源泉・15施設・9浴槽
└── onsen_heuristics.ttl   独自ヒューリスティック: 口語表現、条文表記の言い換え、相談の意図

src/onsen_ontology/
├── namespaces.py    名前空間
├── env.py           `.env` 読み込み（既存の環境変数は上書きしない）
├── graph.py         TTL 読み込みと推論結果のキャッシュ
├── reasoning.py     SPARQL ルール推論（R1〜R7）＋ OWL 2 RL 演繹閉包
├── queries.py       SPARQL 検索レイヤ（エージェントのツールになる）
├── itinerary.py     巡浴プランの生成と法定プロトコル検証
├── agent.py         Bedrock Converse API による温泉爺エージェント
├── verify.py        回答の検算（ツール戻り値との照合）
├── consult.py       相談セッション（申し送り・自動裏取り）
├── corpus.py        比較実験用コーパスの構築（出典URLの取得と Markdown 化）
├── retrieval.py     生テキストの BM25 検索（オントロジーの対抗条件）
├── aligned.py       グラフから「揃えた生ドキュメント」を書き出す（比較条件F）
├── ablation.py      効果検証（4条件×12問＋任意条件E・F の比較と採点）
├── visualize.py     グラフの一部を DOT で図にする
└── cli.py           CLI

docs/
├── domain-analysis.md          Phase 1: ドメイン分析と設計判断、温泉爺ペルソナ定義
├── research-spring-quality.md  一次情報調査（温泉法・鉱泉分析法指針・掲示基準）出典31件
└── research-onsen-data.md      実データ調査（15温泉地）出典35件
```

TTL を4ファイルに分けているのは、**出典と更新サイクルが違う**ため。法定知識の出典は環境省の通知（改訂は数年に一度）、実データの出典は各施設の公式サイト（いつ変わるか分からない）、ヒューリスティックには**出典が無い**（本オントロジーの判断である）。出典の無いものを出典のあるものと同じファイルに置かないという線引きで、テストでも検査している。

## 設計上の要点

実データを集めた結果、素朴な設計が壊れた箇所とその対処。詳細は [docs/domain-analysis.md](docs/domain-analysis.md)。

1. **施設と源泉を分離した。** 草津は源泉ごとに pH が違う（湯畑2.08／万代1.7／煮川2.1）。1施設が複数源泉を使い、1源泉が複数施設に配湯される多対多。
2. **`isKakenagashi` を単一の boolean にしなかった。** 「源泉かけ流し」は法令上の定義がない自主表示で、有馬温泉 金の湯は「放流式（かけ流し）」でありながら加水・加温・塩素消毒をすべて実施している。法定5類型を中間ノードに reify し（「その旨**及びその理由**」が掲示義務）、自称ラベル `claimsKakenagashi` と推論値 `isUnmodifiedSupply` を分けた。
3. **成分値に測定地点と分析年月日を付けた。** 掲示は利用施設ベースが原則だがゆう出口ベースも許容され、値が乖離しうる（掲示基準 4.留意事項）。
4. **「はしご湯」を概念として作らなかった。** 一次情報に出現しない俗語。制約はすべて法定の浴用プロトコル（入浴回数・時間・安静30分・42℃・湯あたり3〜7日）への参照として表現した。
5. **法定知識と独自ヒューリスティックを型で分けた。** `onsen:legalBasis` と `onsen:heuristicRule`、警告の `severity: "legal" | "heuristic"`。「酸性泉のあとは仕上げ湯」は法令ではなく、四万温泉 積善館の「草津の仕上げ湯」という記述に基づく経験則である。
6. **欠損を欠損として持つ。** pH が取れたのは 14/27 源泉、源泉温度は 16/27。推測値では埋めず `onsen:dataStatus` に理由を書いた。
7. **泉質の判定根拠を型で分けた。** 成分値（指針 第1-3表）から判定したものは `onsen:hasQuality`、掲示泉質名や旧泉質名の**表記から読み取った**ものは下位プロパティ `onsen:hasQualityFromName` で主張する。実データで成分値から判定できるのは大涌谷温泉の1源泉だけで、残り26源泉は名称からの読み取りである。玉川温泉は pH1.2 だが水素イオン濃度(mg/kg)が未公表なので**成分値からは酸性泉を導けない**（判定基準は pH ではなく H⁺ 1mg/kg以上）。それでも掲示泉質名「酸性・含二酸化炭素・鉄（Ⅱ）－塩化物温泉」の表記から酸性泉・二酸化炭素泉・含鉄泉・塩化物泉と読める。一方ラドン濃度は名称に現れず未公表なので、放射能泉かどうかは分からないままにしてある。

## 推論

```console
$ uv run onsen stats
{
  "推論前トリプル数": 1680,
  "推論後トリプル数": 4176,
  "追加トリプル数": {
    "R1: pH から液性区分を導出": 13,
    "R2: 源泉温度から泉温区分を導出": 12,
    "R3: 溶存物質から浸透圧区分を導出": 1,
    "R4: 成分値から掲示用泉質を判定（下限値型）": 0,
    "R5: 単純温泉かつ現地pH8.5以上 → アルカリ性単純温泉": 1,
    "R6: 法定4類型すべて非実施 → 無加工供給": 2,
    "R7: 浴用の泉質別禁忌症を持つ泉質 → 皮膚刺激が強い": 2,
    "OWL 2 RL 演繹閉包": 2465
  }
}
```

- **OWL 2 RL（owlrl）** — プロパティチェーン公理（施設→源泉→泉質→適応症）、`owl:inverseOf`、`owl:SymmetricProperty`、クラス階層、プロパティ階層（`onsen:hasQualityFromName` → `onsen:hasQuality`）
- **SPARQL ルール** — 数値比較、閉世界の否定、算術。閾値は Python ではなくグラフ側の宣言（`onsen:minPH` など）から読む

R4 の発火数 0 は実装の不具合ではなく、**実データで成分値が公開されている施設がほぼ無い**ため。ルールの正しさは合成データのテストで担保している。

2つの注意点:

- `owlrl` の `expand()` は**1回では不動点に達しない**（このグラフでは2回目に150トリプル前後増える）。増えなくなるまで反復している。
- **SPARQL ルール → OWL** の順で適用する。逆順だと SPARQL が追加したトリプルに OWL 推論が未適用のまま残り、パイプライン全体が冪等にならない。

推論結果は `.cache/inferred.ttl` にキャッシュされ、TTL と `reasoning.py` の mtime で無効化される。

## 回答の検算

システムプロンプトは「ツールが返した値だけを使う」と命じているが、プロンプトは守られる保証がない。守られたかどうかを `verify.py` が機械的に検査する。

```console
$ uv run onsen ask "草津の湯は美肌にええと聞いたが、効能を教えてくれ。デトックスもできるかい"
（回答）
--- 検算 ---
検算: 2件の指摘
  [warning] folk_expression: 美肌 — 掲示基準の適応症に無い表現
  [warning] folk_expression: デトックス — 法定の記述に無い
```

検出するのは7種類。

| kind | severity | 内容 |
|---|---|---|
| `unsourced_quantity` | error | pH・温度・時間などの単位付き数値が、ツール戻り値にも相談文にも無い |
| `unsourced_term` | error | オントロジーの語彙（施設名・源泉名・泉質名・症状名）を、ツールが返していないのに使った |
| `folk_expression` | warning | 「美人の湯」「保温効果」など法定の記述に無い通俗表現 |
| `missing_disclosure` | warning | 適応症に触れて掲示基準に言及しない（規則2）、経験則を前置きなしで語る（規則5） |
| `missing_tool_call` | error / warning | 巡浴を頼まれて `plan_itinerary` を呼ばないなど、呼ぶべきツールを呼んでいない |
| `paraphrased_term` | warning | 条文表記を要約した言い換え（「病気の活動期（特に熱のあるとき）」→「急性疾患」） |
| `nonstatutory_indication` | error | 現行の掲示基準の適応症一覧に無い効能表記（「虚弱児童」「慢性婦人病」「うちみ」） |

`--revise` を付けると、指摘を温泉爺自身に差し戻して1回だけ書き直させる。上の相談で実際に「美肌」が「皮膚乾燥症」（掲示基準の適応症名）に直った。

設計上の判断が4つある。

1. **単位を要求する。** 単位のない数字を拾うと掲示基準の条番号（`2.(2)① オ`）や箇条書き番号が誤検出される。
2. **相談文の数値・語彙は許容するが、通俗表現は許容しない。** 利用者が言った症状や日数を復唱するのは当然だが、利用者が「デトックス」と言ったことは温泉爺がその語を使ってよい根拠にはならない。
3. **オントロジーの戻り値に出典がある通俗表現は通す。** 「保温」は掲示基準の入浴後の注意（保温及び30分程度の安静）に、「保湿・美肌効果」は四万温泉 積善館の公式記述に実在する。
4. **出典の“ある/なし”と“質”を分ける。** 数値と語彙は文書検索の戻り値も出典として認めるが、通俗表現・条文の言い換え・非法定の効能表記は**グラフ（法定知識）を基準に**判定する。生テキストを引く条件では取得した Web 本文が戻り値になるので、照合だけで済ませると「美人の湯」も「虚弱児童」も出典ありとして通ってしまう。**出典があることと、法定の記述であることは違う。** ツール呼び出しの記録は `ToolCallLog.source` に `ontology` / `documents` を持つ。

検算が使う表はすべてグラフ側にある。語彙は `rdfs:label`、口語表現は `onsen:colloquialExpression`、条文表記の言い換えは `onsen:nonStandardParaphrase`、現行の掲示基準に無い効能表記は `onsen:NonStatutoryIndication` の個体、相談の意図と呼ぶべきツールの対応は `onsen:ConsultIntent` の個体。法令に根拠がないものは `onsen_heuristics.ttl` に隔離し、`onsen:heuristicRule` 注記を付けている。実データを1件足せば検算の網も広がる。

「現行の掲示基準に無い」という主張自体はテストで検査している。`onsen:NonStatutoryIndication` として宣言した語（虚弱児童・慢性婦人病・うちみ・くじき・痔疾・やけど・慢性消化器病・慢性皮膚病）が `onsen_knowledge.ttl` に現れたら落ちる。逆に「五十肩」「打撲」「捻挫」「運動麻痺」「冷え性」は**現行の条文にそのまま出てくる**ので、宣言に含めてはならない。旧基準にあった表記かどうかは一次情報を確認できていないので主張していない。主張するのは「現行の一覧に無い」ことだけである。

限界は残る。検算は「ツール戻り値に無い」ことしか見ないので、**意味の正しさは検査しない**。「塩分が皮膚に膜を張る」のような自由記述の作用機序は、語彙表・通俗表現表・言い換え表のいずれにも無いので素通りする。

## 表現形式の効果検証 — オントロジーか、生テキストか

最初に測ったのは「知識を与えるか否か」だった（素の LLM vs ツールあり）。これでは**オントロジーを作る価値**を測れていない。実務で比較されるべき対抗案は「何もしない」ではなく「**同じ情報を文書として置いて検索させる**」である。そこで問いを立て直した。

> 同じ一次情報を**トリプルに整理する価値はあるのか**。生テキストのままで足りるのか。

```bash
uv run onsen corpus build                          # docs の出典URLを取得して生テキストのコーパスを作る
uv run onsen corpus align                          # グラフから「揃えた生ドキュメント」を書き出す（条件F用）
uv run onsen eval --dry-run                        # 呼び出し計画を確認
AWS_PROFILE=dev-vm uv run onsen eval               # 4条件 × 12問（48回の Bedrock 呼び出し）
AWS_PROFILE=dev-vm uv run onsen eval --conditions F G H   # 追試の3条件（各12回）
uv run onsen eval --report eval-results/*.jsonl    # 保存済みの結果を合算して集計
```

| 条件 | 内容 | ツール | Haiku 4.5 | Sonnet 4.6 |
|---|---|---|---|---|
| A | 素の LLM（人格プロンプトのみ） | なし | 34.3%（35/102） | 44.1%（45/102） |
| B | オントロジーのツールあり | 10個 | 71.6%（73/102） | **92.2%**（94/102） |
| C | ツールあり＋検算の差し戻し | 10個 | **73.5%**（75/102） | 88.2%（90/102） |
| D | **生テキストの文書検索（BM25）** | 2個 | 67.6%（69/102） | 87.3%（89/102） |
| F | **同じ内容を揃えた生ドキュメントにして BM25 検索** | 2個 | **88.2%**（90/102） | **95.1%**（97/102） |
| G | B のツール表面を直した版（追試） | 11個 | **86.3%**（88/102） | 91.2%（93/102） |
| H | F ＋ 計算ツール（追試） | 5個 | 81.4%（83/102） | 93.1%（95/102） |

事実チェック合格率。12問 × 4条件 × 3回 × 2モデル（計288サンプル）の実測値。**分母の102は問数ではなく採点条件の数**である（12問に1〜4個の条件を持たせて計34個、それを3回ずつ = 102）。各条件は同じ温度（0.4）で走らせている。**どのモデルで測ったかは結果の JSONL に `model_id` として記録され、集計にも出る。**

コーパス（条件 D）は `docs/*.md` が出典として記録している URL の全体である（55件のうち51件・35.9万字を取得。失敗4件は理由つきで `manifest.json` に残る）。**人が情報源を選別しない**という定義なので「都合の悪い情報源を外した」という批判が立たない。全チャンクに出典URLと取得日を持たせ、条件 D にも出典を語らせている。片方だけ出典を言えないと、条件の差が出典の有無にすり替わる。

### 結論: 効いていたのは「整理されたデータ」だった

- **生テキスト検索はかなり強い。** D は B に対して Haiku で −4.0pt、Sonnet で −4.9pt。**「オントロジーでなければ届かない」とは言えない**。整理された一次情報が手元にあるなら、BM25 と賢いモデルでほとんどの問には答えられる
- **差が出るのは検算の指摘。** 合格率が近い一方で、D の回答には通俗表現・条文の言い換え・非法定の効能表記が残る
- **そして「揃えた生ドキュメント」（条件F）は B を上回った。** グラフの内容を推論結果なしで同じ書式の Markdown（29文書・2.3万字）に書き出し、条件D とまったく同じツール・同じプロンプトで引かせると **Haiku 88.2%（B +16.6pt）・Sonnet 95.1%（B +2.9pt）**。閉世界の否定（Q9）は 9/9・8/9、未公表の申告（Q11）は 5/9・8/9 まで戻り、非法定の効能表記の指摘は 12件 → **0件**、条文の言い換えは 9件 → **0件**、トークンは D の半分になった。**`isUnmodifiedSupply` を書いていないのに Q9 が解けた**ので、推論エンジンの取り分もここでは出ていない
- ただし **F の文書はグラフから生成している**（`onsen corpus align`）。一次情報を読んで項目を揃え、未公表を未公表と書き、母集合を決める作業を済ませたあとの産物なので、**作るコストはオントロジーと同じ**である。**効いていたのは「整理する作業」で、置き場所（TTL か Markdown か）は成績を変えなかった**という読み方が正確
- **F−B の幅の大半はツール表面の穴だった。** 源泉名で引くツール（`describe_spring_source`）と仕上げ湯の逆向きを足して測り直すと（条件G）、Haiku は 71.6% → **86.3%** に上がり F との差は **1.9pt** に縮む。Sonnet は 92.2% → 91.2% で変化なし（賢いモデルは元から施設を総当たりして回避していた）。**値も辺もグラフにあったのに、引けていなかっただけ**である
- **揃えた文書に計算ツールを足しても伸びなかった**（条件H。Haiku 81.4%、Sonnet 93.1%）。`plan_itinerary` は実際に呼ばれ `missing_tool_call` は 6件 → 2件に減ったが、事実チェックは伸びない。下がった分はプロンプトの追記とサンプリングの揺れが混ざっており切り分けられていないので、言えるのは「足しても伸びなかった」ことだけ
- オントロジー / ナレッジグラフは整理手法として強力な選択肢の1つであり、整理そのものの代わりにはならない
- F は A〜D の288サンプルを測ったあとに足した追試（12問×3回×2モデルで72サンプル）。採点器と問は同一だが、**同時に走らせた実験ではない**

| 指標（36サンプルあたり） | Haiku B | Haiku D | Haiku F | Sonnet B | Sonnet D | Sonnet F |
|---|---|---|---|---|---|---|
| 検算の指摘（合計） | 29件 | **55件** | 13件 | 11件 | **44件** | 17件 |
| うち `folk_expression` | 8 | 18 | 6 | 8 | 20 | 6 |
| うち `paraphrased_term` | 0 | 9 | **0** | 0 | 8 | 2 |
| うち `nonstatutory_indication` | 0 | 12 | **0** | 0 | 1 | **0** |
| 平均トークン | 19,060 | 28,350 | 14,145 | 14,389 | 36,917 | 22,602 |
| 平均レイテンシ | 7.3秒 | 8.9秒 | 6.9秒 | 23.0秒 | 30.6秒 | 25.0秒 |

コーパスは案Aのままで**実際に汚染されている**。「美肌」は8文書、「美人の湯」は1文書（草津 大滝乃湯）、「慢性婦人病」8文書、「うちみ」8文書、「やけど」12文書、「虚弱児童」4文書。大滝乃湯の公式ページの効能書きは「神経痛、関節痛、うちみ、ねんざ、やけど、慢性消化器病、病後回復期、美肌、慢性婦人病」で、このうち5語は現行の掲示基準の適応症一覧に無い。生テキストを引いた回答はこれをそのまま復唱する（汚染の問 Q12 は Haiku D で 0/9）。

### 問ごとに見ると分業がはっきりする

| 問 | 軸 | Haiku B / D / F | Sonnet B / D / F |
|---|---|---|---|
| Q2 | 照会: 源泉ごとの粒度（湯畑2.08・万代1.7・煮川2.1） | 3/12 / **12/12** / **12/12** | 12/12 / 12/12 / 12/12 |
| Q6 | 判定: 施設→源泉→泉質→適応症の連鎖 | **9/9** / 6/9 / **9/9** | **9/9** / 7/9 / **9/9** |
| Q9 | 計画: 閉世界の否定（加水も消毒もしていない施設） | **9/9** / 6/9 / **9/9** | **9/9** / 6/9 / 8/9 |
| Q11 | 不明の申告: 未公表の成分（玉川は放射能泉か） | **6/9** / 2/9 / 5/9 | 6/9 / 5/9 / **8/9** |
| Q12 | 汚染: 通俗表現と旧表記 | 2/9（C は **6/9**）/ 0/9 / **6/9** | **6/9** / 5/9 / 7/9 |

- **Web を丸ごと取った生テキストが負けるのは「書かれていないこと」を扱う問。** 閉世界の否定（Q9）は、施設ごとに「無い」の書き方が違い、4類型を同じ形で並べたページがほとんど無いので数え上げられない。ただし**同じ情報を同じ書式に揃えれば届く**（条件F は 9/9・8/9）。原理的に出せないのではなく、記述が揃っていないのが原因だった
- **生テキストが勝ったのは検索で足りる照会。** Q2 で Haiku の B が 3/12 だったのは、オントロジーに値がある（湯畑源泉 pH2.08）のに**源泉名で引くツールが無い**ためである。施設名でしか引けないので `describe_facility("湯畑")` が空振りする。Sonnet は施設を総当たりして 12/12 に届いた。**整理しても、引ける形で出していなければ意味がない**（Phase 8 の宿題）
- **検算の差し戻しは弱いモデルでしか起動しない。** 汚染の問（Q12）で Haiku は B 2/9 → C 6/9（書き直しは10回発生）。一方 Sonnet は指摘が少なく、36サンプル中**書き直しは2回だけ**。合格率は B 92.2% に対し C 88.2% だが、**落ちた3問（Q3・Q7・Q9）はいずれも書き直しゼロ回**なので差し戻しのせいではない。B と C は指摘が出なければ完全に同じ設定であり、この差はサンプリングの揺れである（3回×12問では問ごとの ±1 を読んではいけない）
- **素の LLM は賢くなるほど裏取りできない記述が増える**（検算の指摘は Haiku A 80件、Sonnet A 164件）。Sonnet A は旧基準の効能表記も8件出した

### 採点器について

- **事実チェック**は一次情報から書き起こした期待／禁止条件（`Check`）で、各条件に根拠となる条文・公表値を必ず持たせている
- **検算**は `verify.py` をそのまま流用する。A はツール戻り値が空なので数値・語彙は定義上すべて「出典なし」に倒れる。条件間で比較できるのは事実チェックの合否であり、指摘件数は分布として読む
- 採点条件を直したときは `onsen eval --report` が保存済みの全サンプルを現在の条件で再採点する（結果を都合よく動かさないため）。実測後に2件直した。「仕上げ湯に刺激の強い泉質を勧めていない」の禁止条件が「酸性泉・硫黄泉の後の仕上げ湯として推奨される」という**正しい説明**を落としていたので勧める形だけを見るようにし、「源泉ごとに違うと言う」という言い回し依存の期待条件を「温泉地単位の pH を単一の値として述べない」という禁止条件に置き換えた。どちらも再発をテストで固定している
- 問セットは JSONL に `question_set` として記録する。8問時代の結果に12問の採点条件を当てると、同じ `Q3` が別の相談を指すので数字が壊れる。`rescore` は問セットが一致するものだけ再採点する

問の設計・採点条件・集計は `tests/test_ablation.py` で固定している（合成回答で満点・不合格の両方を確認）。

なお「プロンプトだけ厳しくした LLM」（条件 A+）は前の実験で役目を終えた。口調と規律はプロンプトだけで半分以上改善するが、公表値には届かない。`--conditions A+` で今も走る。

## テスト

```bash
uv run pytest              # 177 passed, 1 skipped
uv run ruff check .
```

実 Bedrock を呼ぶテストはオプトイン。

```bash
AWS_PROFILE=dev-vm ONSEN_TEST_BEDROCK=1 uv run pytest -k bedrock
```

テストの方針は「**一次情報との対応が崩れたら落ちる**」こと。

- 掲示用泉質はちょうど10種類
- 判定閾値が指針 第1-3表と一致する
- 泉質別禁忌症を持つのは酸性泉と硫黄泉の2泉質のみ
- 硫酸塩泉の浴用適応症は塩化物泉と同一（原文「塩化物泉に同じ」）
- 含有成分別禁忌症の計算が掲示基準の条文中の計算例と一致する
- すべての源泉に出典URLがある
- 法令に根拠のないプロパティには `onsen:heuristicRule` 注記がある
- 独自ヒューリスティックが法定知識・実データのファイルに混ざっていない
- 泉質を `onsen:hasQuality` で直接主張しているのは成分値が揃っている源泉だけである
- 推論が冪等である
